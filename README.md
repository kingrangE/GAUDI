# and-you

> **AI Agent 활용·검증 역량 평가 플랫폼** — 제 14회 AI SW 해커톤 출품작 (제 14회 소프트웨어융합대학 SWAI 해커톤)

`and-you`는 **사람이 AI 에이전트를 얼마나 잘 지시하고, 그 결과를 얼마나 잘 검증·거부하는가**를
평가하는 플랫폼입니다. 단순히 정답/오답을 채점하는 것이 아니라, 한 사람이 *어디까지 알고 어디부터
모르는지*를 LLM-as-a-judge로 드러내어 다각적으로 분석합니다.

> ⚠️ **현재 상태: 초기 스캐폴드 / 개발 중.** 이 문서는 목표 서비스(To-Be) 기준으로 작성되었습니다.
> 현재 코드베이스는 거버넌스 문서·CI 스캐폴드·스킬을 갖춘 단계이며, 기능 구현이 진행 중입니다.

---

## 무엇을 평가하는 서비스인가

AI Agent로 코드를 작성하는 시대가 열리면서, 전통적인 코딩테스트와 과제 전형은 개발자에게 실제로
필요한 역량을 더 이상 충분히 측정하지 못합니다. 알고리즘 구현 자체는 에이전트가 대신해 주기 때문에,
이제 변별력은 **에이전트를 지시·검증·거부하는 사람의 역량**에서 나옵니다.

`and-you`는 다음 질문에 답합니다.

- AI에게 **의도를 얼마나 명확하게** 지시하는가? (명세·프롬프트 설계)
- AI의 답변을 **맹목적으로 수용하지 않고 검증·거부**할 수 있는가?
- 에이전트를 **효율적으로 운용**하는가? (Context Engineering)
- 전통 코테/CS에서, 정답을 넘어 **왜 그 답을 냈고 어디까지 이해했는지**를 설명할 수 있는가?

---

## 왜 만드는가 (배경 / 페인 포인트)

1. **에이전트 시대와 평가의 괴리.** Agent Coding이 보편화되며 기존 코딩테스트/과제 전형은 개발자에게
   실제로 필요한 역량을 적절히 평가하지 못합니다. 핵심 참고 문헌인 *When Code Becomes Abundant:
   Redefining Software Engineering Around Orchestration and Verification* 는 코드가 풍부해진 시대의
   핵심 역량을 다음과 같이 재정의합니다.
   - **아키텍처 추론** — 코드 정리 능력이 아니라, 자동 생성에 대한 *제약과 감사를 설계*하는 능력
     (나쁜 아키텍처의 자동 생성 = 인간 통제력의 상실로 규정).
   - **실행 가능한 명세로서의 테스트** — 동작 보장을 명세로 작성하는 능력.
   - **의도의 명확한 표현** — 구현된 각 부분이 정말 자신의 의도대로 되었는지 확인하는 능력.
   - **거부할 줄 아는 판단** — 원하는 방향이 아닌 출력을 검토하여 거부하는 판단력.
   - **트레이드오프 판단** — 기술 선택의 득실을 가늠하는 능력.

2. **사무직의 AI 프롬프팅 격차.** LLM/Agent는 개발자뿐 아니라 사무직의 생산성과도 직결되지만,
   프롬프팅 역량이 부족하면 좋은 결과를 얻기 어렵습니다. 이 격차 자체를 측정 대상으로 삼습니다.

3. **단순 정답/오답의 한계.** 전통 코테/CS를 정답 여부로만 채점하면 사람의 다각적인 장단점을 분석할 수
   없습니다. `and-you`는 **왜 그런 답을 냈는지**까지 확인할 수 있게 하여, 같은 점수 안에서도 차이를 드러냅니다.

## 무엇을 평가하는가 (평가 영역)

평가는 크게 세 축으로 구성됩니다.

### ① AI Agent 활용 개별 역량

| 평가 항목 | 측정하는 역량 | 평가 방식 | 산출물 |
|---|---|---|---|
| **테스트 설계** | 허점 발견 능력 | 허점이 있는 코드를 제공 → 응시자가 발견한 결함을 작성 → AI가 이를 바탕으로 채워 실행·채점 | 결함 발견율 |
| **거부 능력** | AI 맹신 거부 (잘못된 설계 탐지) | AI 생성물에 **0~N개의 결함을 무작위 주입**, 응시자가 잘못된 부분을 잡아내는지 **3회 반복** | **Precision / Recall** |
| **명세 설계** | 기술 이해·지시 구체성 | 동일 지시를 **10회 비동기 실행** 후 답변 간 분산도 측정 (temperature를 극단적으로 설정해, 지시가 추상적일수록 결과가 크게 갈리게 설계) | 답변 일관성 점수 |
| **Context Engineering** | 에이전트 효율적 운용 | 프로젝트 구성·파일 정보를 제공하고 `CLAUDE.md` 작성을 요청 → 컨텍스트 설계 품질 평가 | 컨텍스트 설계 점수 |
| **개발 프롬프팅** | 알고리즘 이해 | 어려운 알고리즘 문제를 **AI만으로** 풀기(코드 직접 수정 불가, 골드 3~4 / 프로그래머스 Lv2~3 난이도) | 해결 여부·이해도 |

> **명세 설계 예시** — 주제: "로그인/회원가입 기능 구현"
> - ❌ 나쁜 지시: "로그인 회원가입 기능 구현해줘"
> - ✅ 좋은 지시: "FastAPI로 로그인/회원가입을 구현하고, 회원 정보 테이블은 PostgreSQL에 저장.
>   저장 항목과 PK는 ~~~, 세션 관리와 토큰 처리는 ~~~ 방식으로 …"
>
> 지시가 구체적일수록 10회 실행 결과의 편차가 작아집니다.

### ② 사무직 Prompting

개발이 아닌 **사무·데이터 분석/인사이트 도출** 맥락의 문제를 출제하여, 비개발 직군의 AI 활용
프롬프팅 역량을 평가합니다.

### ③ 전통 코테 / CS 심층 평가

정답 여부를 넘어 **이해의 깊이**를 분석합니다.

- **부분 정답 분석** — 예: DP 구현에서 한 군데 부호 하나가 틀린 사람과, 아예 접근이 틀린 사람을 구분.
  "이건 잘하고 저건 부족하다"를 짚어 줍니다.
- **동점자 변별** — 같은 100점이라도 코드 퀄리티 차이를 인사이트로 제공.
- **CS 서술형 채점 루브릭** — 서술형으로 답하게 하여 이해도를 명확히 드러냅니다.

  | 응답 유형 | 점수 |
  |---|---|
  | 정확히 맞춤 | **+5** |
  | 솔직히 모른다고 답함 | **−2** |
  | 부분적으로 아는 데까지만 적음 | 부분 점수 |
  | 애매하게 아는 척하며 딴소리로 틀림 | **−5** |

- **두 가지 리포트**
  - **요약 리포트** — 부족한 키워드 위주(즉시 평가용).
  - **분석 리포트** — 더 상세한 진단(면접 심화 질문용).

> 전통 코테의 의의는 "알고리즘을 *왜* 선택했고, 그 알고리즘을 *알고* 구현했는가"에 있습니다.
> `and-you`는 알고리즘 풀이 여부 자체보다, 그 선택과 이해를 요약·분석해 줍니다.

## 공통 기능

- **역할 구분** — 평가자(응시자) / 채점자(관리자) 권한 분리
- **로그인 / 회원가입**
- **문제 세트 구성** — 유형별로 문제 세트를 구성·관리
- **풀이 화면** — 실제 문제를 푸는 화면 (시간/타이머 제공)
- **결과 조회** — 응시자별 평가 결과 화면
- **관리자 페이지** — 전체 응시 결과 통합 조회

---

## 신뢰도 확보 / 채점 방식

- **LLM-as-a-judge** — 모든 채점은 백엔드에서 LLM이 루브릭에 따라 수행.
- **반복 실행으로 분산 측정** — 거부 능력은 3회, 명세 설계는 10회 반복 실행하여 우연을 배제.
- **정량 지표** — Precision/Recall, 답변 일관성 등 수치로 환산해 비교 가능하게 함.

## 데모 시나리오

1. 노트북 3대에서 3명이 동시에 평가를 진행.
2. 평가 종료 후, 한 대에서 **관리자 페이지**를 열어 각 인원의 결과를 통합 확인.
3. 누가 어디서 강하고 약한지 한눈에 비교 → 합·불 판정.

## 아키텍처 / 기술 스택

단일 **모노레포**로 구성됩니다.

- **Frontend** — Next.js (React, TypeScript) · `frontend/`. LLM을 직접 호출하지 않는 순수 UI.
- **Backend** — FastAPI (Python 3.12) · `backend/`. **모든 LLM / LLM-as-judge 호출이 여기에 중앙화**됩니다.
- **Database** — PostgreSQL.
- LLM 프로바이더/모델 설정은 백엔드의 단일 설정 모듈에 모읍니다 (모델 ID를 여기저기 흩지 않음).

```
and-you/
├── frontend/        # Next.js (React, TS)
├── backend/         # FastAPI (Python 3.12) — LLM/judge 호출 전부
├── .claude/skills/  # 팀 공용 워크플로 스킬 (ship-feature, test-writing)
├── .codex/          # Codex용 슬래시 커맨드 (스킬과 동일 소스 심링크)
├── .github/         # CI 워크플로 + PR 템플릿
├── CLAUDE.md        # 동결된 루트 거버넌스 (= AGENTS.md, 수정 금지)
└── AGENTS.md
```

## 개발 셋업 (Getting Started)

### Backend (`backend/` 에서 실행)

```bash
pip install -e ".[dev]"     # 또는: uv sync
ruff check .                # lint
pytest                      # tests
pytest tests/test_x.py::test_name   # 단일 테스트
```

### Frontend (`frontend/` 에서 실행)

```bash
npm install
npm run lint                # eslint
npm run typecheck           # tsc --noEmit
npm test                    # vitest run
npm test -- src/foo.test.ts # 단일 테스트 파일
```

### 환경 변수 / 시크릿

- API 키·DB URL 등 시크릿은 **`.env`(git-ignored)** 에만 둡니다. 값 없는 `.env.example`을 참고해 복사하세요.
- **시크릿은 절대 커밋하지 않습니다.**

## 기여 규칙 (요약)

- **브랜치** — 항상 최신 `main`에서 분기. 이름은 `type/owner/short-desc`
  (`type ∈ feat|fix|chore|docs|refactor|test`, `owner ∈ hyeoksin|gilwon|minsu`).
  예: `feat/gilwon/rejection-eval`. **`main` 직접 push 금지** (브랜치 보호).
- **커밋** — [Conventional Commits](https://www.conventionalcommits.org/), **제목은 영문**, 본문은 한국어 가능.
  **AI co-author 트레일러 금지** (`Co-Authored-By: Claude` 등 부착 금지).
- **PR 머지 게이트** — ① 팀원 1명 승인(본인 PR 자가 승인 불가) + ② 그린 CI(both backend/frontend).
  **Squash-merge** 후 **브랜치 삭제**, `main`은 항상 linear·demo-able.
- **테스트 필수** — 테스트 없이 "done"도 PR도 없음. 단위 테스트에서는 **LLM을 mock**.

> 상세 규칙은 루트 [`CLAUDE.md`](./CLAUDE.md) / [`AGENTS.md`](./AGENTS.md)(동결, 동일 내용)와
> `.claude/skills/` 의 **`ship-feature`**, **`test-writing`** 스킬을 참고하세요. Codex 사용자는
> `.codex/README.md` 를 참고해 동일 워크플로를 슬래시 커맨드로 사용합니다.
