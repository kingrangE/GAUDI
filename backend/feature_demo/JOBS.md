# 공개 체험 공용 작업·진행 상태

구현 단위: 2차 공통 작업 저장·큐·진행 상태
작성일: 2026-11-04
선행 기능: [세션·소유권](SPEC.md), PR #64

긴 평가의 원본과 상태를 DB에 먼저 저장하고 작업 ID로 조회한다. 첫 실행 어댑터는
컨텍스트 평가이며, 기존 `build_report()`와 루브릭을 재사용한다. 3차에서 나머지 기능과 기존
프론트엔드도 연결했다. 최신 전체 기능 계약은 [어댑터 명세](ADAPTERS.md)에 기록한다.

## API 계약

| 요청 | 동작 |
|---|---|
| `POST /api/demo/jobs` | 원본 저장·전달 시도 후 `202`와 작업 상태 반환 |
| `GET /api/demo/jobs/{job_id}` | 소유자의 작업 상태·단계·완료 단위·진행률 조회 |
| `GET /api/demo/jobs/{job_id}/result` | 완료된 실제 리포트 조회. 미완료·실패는 `409` |
| `POST /api/demo/jobs/recover` | 관리자 전용 전달 복구·중단 상태 조정. 최대 100개씩 처리 |

접수·개인 조회에는 유효한 데모 쿠키가 필요하다. 다른 세션의 작업은 `404`이며
관리자 토큰도 개인 조회 권한을 우회하지 않는다. 공개 모드가 비활성화되면 개인 작업
API는 `404`다. 원본 입력·입력 해시·실행 lease는 공개 상태 응답에 포함하지 않는다.

접수에는 `Idempotency-Key` 헤더가 필요하다. 길이는 1–128자이며 영문·숫자와
`._:-`를 허용한다. 본문 예시는 다음과 같다.

```json
{
  "feature": "context_engineering",
  "action": "evaluate",
  "input": {
    "project_id": "todo-api",
    "claude_md": "프로젝트의 실행 방법과 작업 규칙"
  }
}
```

알려진 프로젝트와 비어 있지 않은 입력만 받는다. 이 API의 입력 문서는 최대 200,000자다.
미지원 기능·동작이나 추가 필드는 거절하며, 클라이언트가 실행 함수 경로를 지정할 수 없다.

같은 세션·같은 키·같은 본문은 기존 작업 ID를 반환한다. 같은 키에 다른 본문을 보내면
`409`다. 이 규칙은 DB의 `(session_id, idempotency_key)` 유일성 제약과 정규화한 JSON의
SHA-256 해시로 검사하므로 별도 API 프로세스의 동시 요청에도 적용된다.

## 저장과 실행

`DemoJob`은 소유 세션, 원본 입력, 기능·동작, 상태, 전달 상태, lease, 진행 단위,
결과·공개 오류 코드와 시각을 저장한다. DB 커밋이 완료된 뒤 Redis에 작업 ID만 전달한다.
DB와 Redis를 하나의 트랜잭션으로 묶지는 않는다. 전달 실패 시에도 DB 원본과 작업 ID를
보존하고 `dispatch_status=error`로 반환해 복구 대상으로 식별한다.

RQ 3.0 이상의 `unique=True`와 고정 RQ 작업 ID를 사용해 중복 전달을 막는다.
추가로 워커가 `queued → running`을 조건부 UPDATE로 점유한다. 중복 메시지가 실제로
도착하더라도 이미 실행·종료된 작업은 평가하지 않는다. 이는 외부 공급자 호출의
정확히 한 번 실행이나 SDK 내부 재시도까지 없앤다는 보장은 아니다.

워커는 점유 시 소유 세션의 유효 기간을 다시 검사한다. 진행·결과 저장은 점유한 lease와
`running` 상태를 함께 비교한다. 중단 처리 이후 늦게 도착한 실행 결과는 저장하지 않는다.
작업마다 새 async engine과 세션을 만들고 종료 시 정리하여 반복 `asyncio.run()`에서
이전 이벤트 루프의 DB 연결을 재사용하지 않는다. 평가 스레드는 AsyncSession을 공유하지 않는다.

`python worker.py`는 기존 `grading`과 신규 `demo` 큐를 함께 처리한다.
신규 큐의 작업 제한 시간은 `DEMO_JOB_TIMEOUT_SECONDS`이며 기본값은 900초다.
API의 신규 큐 접근은 Redis 연결·읽기에 각각 3초 제한을 두고 자동 재시도를 하지 않는다.
이는 전체 요청이 반드시 3초 안에 종료된다는 의미는 아니다.

## 실제 진행률과 완료 조건

컨텍스트 평가의 진행 단위는 네 평가 축이다. 정적 검사 두 축이 끝나면 2/4,
커버리지 처리 후 3/4, 경계 처리 후 4/4를 기록한다. LLM이 없으면 기존과 같이 해당
축을 사용 불가로 표시하고 정적 결과를 반환한다. 진행률은 예상 남은 시간이나 LLM 호출 수가 아니다.

진행 단위는 절대 완료 수로 저장하며 이전 값보다 클 때만 갱신한다. 같은 이벤트의
중복 처리나 지연 도착으로 수치가 두 번 증가하거나 감소하지 않게 한다.
평가 축이 모두 끝나도 `running`이면 최대 99%이며, 실제 리포트의 스키마·프로젝트 일치·
채점 완료 여부를 검증하고 결과와 `completed`를 함께 커밋한 뒤에만 100%를 반환한다.
실패한 평가를 샘플 성공 결과로 바꾸지 않는다.

## 명시적인 복구

관리자가 인증 헤더를 보내 `POST /api/demo/jobs/recover`를 호출한다.
`next_cursor`가 있으면 `?after={next_cursor}`로 다음 묶음을 처리한다.
자동 스케줄이나 주기 실행은 이번 변경에 추가하지 않았다.

| DB 상태와 Redis 관측 | 처리 |
|---|---|
| queued, Redis 작업 없음 | 저장된 동일 작업을 전달 |
| queued/running, Redis가 실행 대기·실행 중 | 실행 상태 유지 |
| queued/running, Redis가 failed/stopped/canceled/finished인데 DB 미완료 | `worker_interrupted` 실패로 확정, 자동 평가 재실행 없음 |
| running, Redis 작업 정보 없음 | `unresolved`로 보고. 실행 종료를 추측해 재실행하지 않음 |
| DB completed/failed | 복구 스캔에서 제외 |

원본 오류 메시지에는 프롬프트나 공급자 정보가 포함될 수 있어 공개 상태에는
`evaluation_failed`, `session_expired`, `worker_interrupted` 같은 코드만 저장한다.
Redis 자체가 응답하지 않으면 관리자 복구 API는 일반화한 `503`을 반환한다.

## Redis 설정과 도입

Compose에 AOF(`appendonly yes`, `appendfsync everysec`)와 `redis-data` 볼륨을 추가했다.
이는 향후 Compose 적용 시 사용하는 설정이다. 이번 작업에서 기존 Redis 컨테이너를
재생성하거나 실제 재시작 후 영속성을 검증하지는 않았다. 기존 컨테이너의 데이터가
새 볼륨으로 자동 이전된다고 가정하지 말고, 큐 작업을 확인·처리하고 필요한 데이터를
보존한 뒤 운영 절차에 따라 적용한다. 작업 상태의 기준은 PostgreSQL이다.

새 `demo_jobs` 테이블은 기존 앱 시작 시 `create_all()`로 생성한다. API·워커는
같은 코드와 DB 설정을 사용해야 한다. RQ 결과 메타데이터 보관 24시간과 DB 평가 데이터
보관 정책은 별개이며, DB 정리는 후속 단위에서 구현한다.
