# 명세 설계 (feature_spec_design)

> **담당:** BE / minsu
> **평가 항목:** 명세 설계 · **측정 역량:** 기술 이해·지시 구체성 · **산출물:** 답변 일관성 점수
> (README ① "AI Agent 활용 개별 역량" 표 참조)

## 1. 목적 (무엇을 측정하나)

응시자가 **AI에게 개발을 얼마나 구체적으로 지시하는가**(명세·프롬프트 설계 역량)를 측정한다.
핵심 가설: **지시가 구체적일수록 같은 지시를 여러 번 실행해도 결과가 수렴하고, 추상적일수록
발산한다.** 응시자가 명시하지 않은 기술 결정(언어/DB/인증 방식 등)은 모델이 매번 다르게
채우기 때문이다. 따라서 **결과의 일관성**을 지시 구체성의 프록시로 사용한다.

## 2. 평가 아이디어 (핵심 메커니즘)

1. 개발 과제(brief)를 제시한다. 예: "로그인/회원가입 기능 구현".
2. 응시자는 **하나의 지시(프롬프트)** 를 작성한다.
3. 그 지시를 **고정·극단적 temperature** 로 **N회(기본 10회) 비동기 실행**한다.
4. 생성된 N개의 결과에서 **핵심 설계 결정**을 LLM 판정자가 추출하고, 항목별 **일치도**를
   계산한다(+모델 비의존 lexical 유사도 보조 지표).
5. 일치도를 **답변 일관성 점수**(0~100)로 환산하고, **갈린 결정 항목**을 피드백으로 돌려준다.

> 핵심 직관: temperature를 극단적으로 높여 **명시되지 않은 결정일수록 크게 갈리도록** 설계한다.
> 구체적 지시는 결정을 고정하므로 고온에서도 결과가 수렴한다.

### 예시 — 주제: "로그인/회원가입 기능 구현"
- ❌ 나쁜 지시: "로그인 회원가입 기능 구현해줘" → DB·인증·토큰 처리 등이 매 실행 갈림 → 낮은 일관성
- ✅ 좋은 지시: "FastAPI로 구현, 회원 테이블은 PostgreSQL, PK는 UUID, 비밀번호는 bcrypt,
  세션은 JWT를 HttpOnly 쿠키로 …" → 결정이 고정됨 → 높은 일관성

## 3. 입력 / 출력 (계약)

**입력**
- 과제 brief + 숨겨진 **결정 항목(dimension) 루브릭** (응시자에게 비공개)
- 응시자 지시 1개
- 실행 설정: 생성 모델·극단 temperature·샘플 수, 판정 모델 — 백엔드 중앙 config(`llm/config.py`)에서 주입

**출력**
- 항목별 일치도(분포·최빈값·발산 여부)
- 전체 평균 일치도 + lexical 유사도
- **답변 일관성 점수**(0~100) + 등급 + **명시되지 않아 갈린 항목** 목록 + 피드백

## 4. 처리 흐름

```
응시자 지시 1개 (과제 brief는 generator에 전달하지 않음 — 지시가 곧 유일한 입력)
  → 고온 모델로 N회 비동기 생성 (generator)
  → 판정 모델로 각 샘플의 결정 추출 → 항목별 일치도 (analyzer)
  → 일치도(주) + lexical 유사도(보조) → 답변 일관성 점수 (scorer)
  → 갈린 항목 = 응시자가 명시하지 않은 결정 (피드백)
```

## 5. 설계 결정 ↔ 코드 매핑

| 결정 | 선택 | 위치 |
|---|---|---|
| 생성 모델 | 일반 모델, **극단 temperature**(기본 1.6) | `llm/config.py` `get_gen_settings` |
| 판정 모델 | 저온(0.0) 결정 추출 | `llm/config.py` `get_judge_settings` |
| 동시 실행 | `asyncio.gather` + `to_thread` 로 N개 동시 생성/판정 | `generator.py`, `analyzer.py` |
| 일관성 측정 | 항목별 최빈값 점유율(주) + 평균 pairwise 유사도(보조) | `analyzer.py` |
| 채점 | 일치도 85% + lexical 15% 가중, 발산 항목 추출 | `scorer.py` |

- 모듈: `models` · `tasks`(루브릭 포함) · `generator`(LLM seam) · `analyzer`(판정+집계) ·
  `scorer` · `evaluator` · `api`(FastAPI 라우터, 조립용).
- 결정 루브릭은 **TaskPublic에서 redact**(개수만 노출) — 응시자에게 정답 명세를 흘리지 않는다.
- 테스트(`backend/tests/test_spec_design_*.py`): generator·analyzer·scorer·api. LLM은 fake client로 목킹.

## 6. 공통 제약 (리포 규칙)

- 모델 선택/호출은 **백엔드 중앙 config**에서 주입. 시크릿은 `.env`만.
- 단위 테스트에서 **LLM을 목킹**: 생성·집계·채점 로직을 결정적으로 검증. 실모델 통합 테스트는 소수만.
- 독립 폴더 개발 후 공용 evaluator 인터페이스로 플랫폼에 **조립**.

## 7. 남은 작업 (조립/후속)
- 라우터를 메인 FastAPI 앱에 mount (전체 기능 조립 단계).
- 판정 비용 절감: 단일 판정 호출로 N개 샘플 일괄 추출(현재는 샘플당 1회).
- 의미 기반 유사도(임베딩) 보조 지표 추가 검토.
- solver/judge 실모델 통합 테스트 1~2개(키 있을 때만, skip 마커).
- `llm/` seam은 `feature_dev_prompting`과 공유 — 조립 시 한 번만 반영(중복 제거).
