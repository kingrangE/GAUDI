# 컨텍스트 엔지니어링 (feature_context_engineering)

> **상태:** 추상 명세 (구현 전). "무엇을 만들 것인가"만 정의한다.
> **담당:** BE / minsu
> **평가 항목:** Context Engineering · **측정 역량:** 에이전트 효율적 운용 · **산출물:** 컨텍스트 설계 점수
> (README ① "AI Agent 활용 개별 역량" 표 참조)

## 1. 목적 (무엇을 측정하나)

응시자가 **낯선 프로젝트에 에이전트를 효율적으로 붙이기 위한 컨텍스트를 설계하는 역량**을 측정한다.
구체적으로는, 프로젝트 구성·파일 정보를 보고 그 프로젝트용 **`CLAUDE.md`를 서술형으로 작성**하게 하여
"에이전트가 헤매지 않도록 핵심 맥락을 추려 전달하는 능력"을 본다.

- 이 역량은 **신규 합류자/온보딩의 실제 핵심 스킬**과 같다: 처음 본 레포에 빠르게 정확한 에이전트
  컨텍스트를 세팅하는 능력.
- 인접 기능과의 구분:
  - **② 거부 능력**은 *AI 출력의 비평가*로서 잘못된 것을 **탐지**(Precision/Recall)한다.
  - **④ Context Engineering**은 *에이전트의 세팅 담당*으로서 좋은 맥락을 **생성**한다. 응시자는
    아무것도 탐지하지 않는다 — 깔아줄 뿐이다.

## 2. 평가 아이디어 (핵심 메커니즘)

1. 샘플 프로젝트 1개를 제시한다 — **디렉토리 트리 + 각 파일 내용 + 짧은 프로젝트 설명**.
2. 응시자는 그 프로젝트를 탐색하고 **서술형으로 `CLAUDE.md`를 작성**한다.
3. 작성한 `CLAUDE.md`를 **제출**로 받아 저장한다.
4. 제출물의 채점은 **별도 트랙**으로 둔다(§5). 이 기능 자체는 **채점 없이 완결**된다 — 문제를
   보여주고 `CLAUDE.md`를 받는 것까지가 본 기능의 책임이다.

> dev-prompting과의 대응: 거긴 "문제 + 테스트케이스 → 코드 제출 → 샌드박스 채점"이고, 여긴
> "**프로젝트 + 설명 → CLAUDE.md 제출 → (채점은 별도 트랙)**". 문제 정의와 제출 계약까지가 BE 책임.

## 3. 입력 / 출력 (추상 계약)

**입력**
- 프로젝트 정의: 디렉토리 트리 + **각 파일의 전체 내용**(좌측 패널에서 파일 클릭 시 내용 표시) +
  짧은 프로젝트 설명(brief)
- 응시자 제출: **서술형 `CLAUDE.md` 텍스트**

**출력**
- 제출 저장/조회 결과 (프로젝트 id, 제출된 `CLAUDE.md`, 메타데이터)
- 평가 결과: **placeholder** — 점수 산출은 별도 채점 트랙에서 채운다(§5)

## 4. 처리 흐름 (추상)

```
프로젝트 제시 (트리 + 파일 내용 + 설명)
  → 응시자가 CLAUDE.md 서술 작성 (좌: 프로젝트 / 우: 서술형 에디터)
  → 제출 수신·저장
  → 채점기 seam 호출 (지금은 no-op / placeholder)
  → (별도 트랙) 컨텍스트 설계 점수 산출
```

좌/우 UI 대응:

| | 프론트 | 백엔드(본 SPEC) |
|---|---|---|
| **좌측** | 디렉토리 트리 + 파일 뷰어 + 설명 렌더 | `Project` 페이로드 서빙(트리 + 파일 내용 + brief) |
| **우측** | 서술형 텍스트 에디터 | 제출 `Submission`(`CLAUDE.md` 텍스트) 수신·저장 |
| 채점 | — | **별도 트랙**(seam만 제공) |

## 5. 채점 (별도 트랙 — 본 기능 범위 밖, seam만 제공)

이 기능은 채점 로직을 포함하지 않는다. 대신 채점기를 끼울 **인터페이스(seam)** 만 둔다. 추후 별도
모듈/작업에서 다음 중 하나(또는 둘 다)를 같은 seam에 등록한다.

- **(A) LLM-as-a-judge (별도)** — "좋은 `CLAUDE.md`" 루브릭으로 품질을 채점. 루브릭 원천:
  - 간결성(지시 수 한계 ~150–200, 루트 <60줄 · 전체 <300줄 권장)
  - WHAT / WHY / HOW (스택·구조 / 목적·역할 / 검증·실행 방법)
  - Progressive disclosure(분리 문서 + `file:line` 참조, 코드 스니펫 복붙 금지)
  - 보편성(모든 세션 적용 항목만; task별 핫픽스 금지), bloat·자동생성(`/init`) 지양
  - 참고: humanlayer "writing a good CLAUDE.md", ArthurClune/claude-md-examples(스택별 예시 = few-shot)
- **(B) 효율-delta (결정적, 대안)** — 고정 에이전트가 평범한 과제 묶음을 응시자 `CLAUDE.md`
  **있을 때 vs 없을 때** 풀게 하고, 정답 도달까지의 **노력(턴·툴콜·토큰)** 차이를 점수화. LLM은
  피험자일 뿐 채점은 코드로 결정적.

> 어느 트랙으로 갈지(또는 둘 다)는 **별도 결정**. 본 기능은 그 결정과 무관하게 완결된다.

## 6. 데이터 모델 개요 (확정은 구현 단계에서)

- `FileNode` — `path`, `kind`(file|dir), `content`(file일 때 전체 내용)
- `Project` — `id`, `title`, `brief`(짧은 설명), `files`(FileNode 목록 = 트리 + 내용)
- `Submission` — `project_id`, `claude_md`(서술형 텍스트), (선택) author/session, created_at
- `ContextScorer` (Protocol) — `score(submission, project) -> ComponentScore`. **별도 트랙이 구현**.
- `EvaluationResult` — placeholder. 등록된 채점기가 없으면 점수 비어 있음.

## 7. 풀어야 할 결정 사항 (Open questions)

- 샘플 프로젝트 출처·구성(자체 제작 전제)·규모(파일 수·언어)와 프로젝트 풀 구성.
- 제출 검증(길이 제한, 빈 제출 처리)과 다회 제출 허용 여부.
- 채점 트랙 확정: (A) LLM-judge / (B) 효율-delta / 둘 다 — **별도 결정**.
- 저장소(DB) 스키마 — 플랫폼 조립 단계에서 확정.

## 8. 공통 제약 (리포 규칙)

- feature 디렉토리 격리: `backend/feature_context_engineering/`. 공용 인프라(LLM provider/model
  config)는 `backend/llm/`. 라우터는 **조립 단계**에서만 앱에 연결.
- 모델 선택/호출은 **백엔드 중앙 config**에서 주입. 시크릿은 `.env`만.
- 테스트는 `backend/tests/`에 `test_context_engineering_*.py`. **LLM은 단위 테스트에서 목킹**.
  본 기능은 LLM을 쓰지 않으므로(채점 별도), 프로젝트 서빙·제출 캡처 등 **결정적 로직**을 검증.
- 독립 폴더 개발 후 공용 evaluator 인터페이스로 플랫폼에 **조립**.
